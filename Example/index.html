1. Setup

The page uses only the public key. Everything that needs the server secret (user tokens, signed links, creating buckets) goes through your server - here the Node example server (sdk/nodejs/Example, npm run server).

"Prepare the test buckets" asks the server to create (once) a public bucket and a private images-only bucket with a size limit and executables blocked, both with the rule set Users' own folders: you read and list, and write or delete only under users/{your id}/.


    


    
    

      
2. Sign in with a Rivium user token (tokenProvider)

      
new RiviumStorage({ apiKey, tokenProvider }): the provider asks your server for a token
        (POST /token); the SDK sends it as x-user-token, renews it before it expires, and retries
        once on token_expired / token_invalid. The rules then know who the user is - and nobody can
        pretend to be someone else.

      
The demo server mints a token for whatever user id you type. A real server signs its user in first
        and mints the token for that user only.

      

        
        
        
      

      

        
        
      

      

      
Using Rivium Auth? No token server needed: its token is the Rivium user token.
        new RiviumStorage({ apiKey, tokenProvider: () => auth.getToken() }) with
        auth = createRiviumAuth({ apiKey }) from @rivium/auth-web, and call
        storage.refreshUserToken() from auth.onAuthStateChanged. This page keeps the demo token
        server so it can sign in as any test user.

      

    


    
    

      
3. Calls wait until a user signs in

      
File requests always need a signed-in user. With no token (the provider returns null), upload,
        listFiles, download, delete ... send nothing and don't fail: they wait.
        storage.isAwaitingUserToken is true and storage.onAwaitingUserToken(cb) is called
        once, so the app can show its sign-in screen. After sign-in, refreshUserToken() (or
        setUserToken(token)) lets every waiting call go on, in order. Option userTokenWaitTimeout
        makes them fail with token_required instead (see Errors).

      

        
      

      
Then press Sign in in section 2: the waiting listFiles() completes by itself.

7. Show an image the right way

      
An <img src> sends no headers. getUrl(id), getDownloadUrl(id) and
        getTransformUrl(id) are API addresses that need x-api-key (and the user token),
        so they never go in an <img>. Use:

      
    
        
  • Public bucket: the file's public link - fetch getUrl(id) with the key, it answers { url }.
    • 
        
  • Private bucket: download(id) (sends the token, follows the rules) and show the bytes as a blob URL,
          or a time-limited signed link from your server.
    • 
      

      

        
        
        
        
      

      

        
        
        
        
      

      

    


    
    

      
8. Links: public, download, signed download, signed upload

      

        
        
        
      

      

      
Signed upload

      
Your server makes an upload link (POST /signed-upload, server secret); the browser PUTs the file straight
        to storage with the same Content-Type; then POST /confirm-upload registers it right away
        (else it appears on the next listing, or within about 20 s). Size, type, executables and rules are checked again when it arrives.

      

        
        
        
      

      

    


    
    

      
9. Image transforms

      
getTransformUrl(id, { width, height, fit, format, quality, blur, sharpen, rotate }) builds the address;
        the page fetches it with headers and shows the bytes. Works on the current file (an image).

      

        
        
        
        
        
        
        
        
      

      

        
        
        
        
        
      

      

      

      


      
Public bucket: header-free link

      
getPublicUrl(publicFileId, options) with the options above returns the public link with them
        (…/public/<bucketId>/<path>?w=200&f=webp). The page puts it in a plain
        <img src>: no headers, and the CDN caches it. Works on the current file when it is an
        image in the public bucket.

      
Use a few fixed sizes: one image keeps at most 50 variants (option combinations); a new one beyond
        that is refused (429 too_many_variants). The same options always give the same URL, so a second view is a cache hit.

      

      

      

      

    


    
    

      
10. Errors

      
Every failure is a RiviumStorageException with statusCode, code (when the server sends one)
        and message. Each button triggers one on purpose and compares it with what is expected.
